# R5: Kind infrastructure

Feature directory: `specs/008-r5-kinds` · Tests: milk

## /speckit-specify

```text
Feature directory: specs/008-r5-kinds
Parent roadmap: specs/pipelines/ROADMAP.md → entry R5. Design: specs/pipelines/design-v7.md (§0 kind, §4.3, §4.9, D-3, D-12).

Let pipeline kinds extend the system without editing the milk package core.

Why: standard pipelines (DMComb, SCAOLoop, AOLinearSimulator) will each need defaults, required compute units, extra tasks and plans, and Vincent will author them later, outside the core.

Requirements:
- A PipelineKind protocol with: kind_id, required_compus (by role name), defaults (TOML defaults shipped with the kind, live), plans, and validate(config).
- Kinds are registered by name in the shared registry. conf.toml selects one with `kind`; the default is generic.
- The kind's defaults feed the lowest confresolve layer (the seam created in R2).
- A kind's plans appear as milk-pipes subcommands. Its tasks are registered like the generic ones.
- validate and required_compus failures raise ConfigError naming the kind and what is missing.
- One stub kind, defined outside the core package, proves that a kind can define its compute units, defaults, an extra task and a plan without any edit to the milk core.

Out of scope: the content of DMComb, SCAOLoop and AOLinearSimulator; plan extensions; entry-point discovery.

Success criteria: the suite is green; tests show the stub kind's defaults in resolved configs, its plan as a subcommand, and validation and required-CompU failures; the stub kind lives outside milk/.
```

Expected `/speckit-clarify` question, which only Vincent can answer: **how does a CLI process load a
kind module that lives outside the core?** Options: the `kind` value is an import path
(`pkg.module:Kind`); an explicitly configured module list; or entry points, which design-v7 lists as
anticipated, not scoped. The design doesn't decide this.
