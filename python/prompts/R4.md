# R4: Rootdir operations

Feature directory: `specs/007-r4-rootdir-operations` · Tests: milk

This is the largest slice. Implement it phase by phase (see below).

## /speckit-specify

```text
Feature directory: specs/007-r4-rootdir-operations
Parent roadmap: specs/pipelines/ROADMAP.md → entry R4. Design: specs/pipelines/design-v7.md (§0 rundir/cold/inconsistent/task/plan/state, §4.0 rule 4, §4.1 incl. the operating-lifecycle diagram, §4.2, §4.6, D-9, D-17–D-20, D-24, D-25) and design-v7-appendix-a.md §A.1 plans, §A.4, §A.5 milk-pipes.

Operate a pipeline from its rootdir, through plans, with a derived state model.

Why: operating a pipeline must work from the authoritative rootdir alone, must detect cold and inconsistent situations, and must clean up exactly what was deployed, even after a resync changed the configuration.

Requirements:
- Rundir $MILK_SHM_DIR/pipe_rundirs/<name>/ (A.4). Deploy creates it, recording the boot_id, the claim (name, loop_number) and the list of FPS names it will create. Deploy refuses if another rundir holds the same name or loop_number. link records the applied (local → remote) pairs there. Teardown removes the rundir.
- State is derived, never stored: cold, deployed, configured, running, inconsistent, or mixed. Consistency means a rundir valid for this boot plus every recorded FPS present. If the current config differs from what was recorded, state reports "config changed since deploy", which is not an inconsistency. state() never raises for these.
- Tasks implement can/forward/success, act on all compute units or on an optional subset, and are registered by name in the shared registry.
- Plans are data: a name, ordered steps (task name plus an optional compute-unit subset) and on_failure (abort | best_effort). The runner checks consistency once per plan, then applies the skip-if-success / can / forward / verify rule to each step. best_effort runs every step and raises one aggregate error.
- Generic plans: deploy = ClaimRundir → InitFPS (in rootdir/work/) → LoadData → ConfStart (abort); start = RunStart; stop = RunStop; teardown = RunStop → DeapplyLinkages → ConfStop → DestroyFPS → ReleaseRundir (best_effort). Teardown and unlink act on the rundir's records, never on the current config.
- deploy accepts cold and any consistent state (re-running it is safe) and refuses inconsistent. Every other plan requires a consistent, non-cold pipeline and otherwise raises ColdSystemError or InconsistentStateError, naming the command to run. teardown works in any state.
- The FPS working directory is rootdir/work/.
- conf.toml may restrict plans with a `plans` key, limited to the names its kind allows.
- milk-pipes operates on a ROOTDIR only. Its subcommands are generated from the plan registry, plus state, link and unlink. The old spool, sys and nuke commands and the tasks they used are removed, and their tests are migrated.

Out of scope: kinds beyond generic (R5); locks; concurrent plans; atomicity; the CLI error handler.

Success criteria: the suite is green; tests cover cold/consistent/inconsistent detection (stale boot_id, missing recorded FPS, FPS without rundir), uniqueness refusal, deploy idempotence and resumption from the partial deployed state, teardown after a resync that changed the compute-unit set (no FPS leaked, no foreign link removed), the on_failure policies, and the generated subcommands.
```
