    moka: plans and tasks¶

    The built-in plans and tasks, how a plan runs, and how to write and register your own plans.

    Audience: Integrator · See also: Operating · Configuration · Internals: task contract · Glossary

    A task is one idempotent action on the live pipeline, on the whole pipeline or on a CompU subset. Without a subset, a task acts on all CompUs, except RunStart (the runstart list), SetLoopOff (the cacao-fpsexec-mfilt CompU), SetLinResp, WaitLinResp (the cacao-fpsexec-cacaoac-measlinresp CompU) and LoadCM (refuses). A plan is a name, ordered steps (a task name and an optional CompU subset), a failure policy and the states it accepts to start from. Registries: PLANS in moka.operate.plans, TASKS in moka.operate.tasks; a pipeline adds its own (§4).

    1. Built-in plans¶

    Plan Steps on_failure accepts
    deploy ClaimRundir → InitFPS → LoadData → ConfStart abort cold_or_consistent
    teardown RunStop → DeapplyAllLinkages → ConfStop → KillTmux → DestroyFPS → ReleaseRundir best_effort any
    runstart RunStart abort consistent
    runstop RunStop best_effort any
    mlat RunStart[acquWFS] → RunStart[mlat] → WaitRunEnd[mlat] abort consistent
    mkpokes MakePokes abort consistent
    measlinresp RunStart[acquWFS] → SetLinResp → RunStart[measlinresp] → WaitLinResp abort consistent
    mkcm MakeCM abort cold_or_consistent
    spool SetLoopOff → RunStop → LoadCM → RunStart[acquWFS] → RunStart → SetLoopOff abort consistent
    takeref RunStart[acquWFS] → TakeRef abort consistent
    takedark TakeDark abort consistent

    mlat needs CompUs named acquWFS and mlat. It leaves acquWFS running.

    moka mkpokes [TYPE] writes the poke cube <rootdir>/calib/RMmodesDM.fits (float32, header POKETYPE) over the actuators of the [dmhint] mask, which it needs. TYPE is hadamard (default: next_pow2(Nact) slices) or zonal (one actuator per slice). A cube already of that type and DM size is left alone; a hand-made one (no POKETYPE) is replaced. The cube is FITS (NAXIS1, NAXIS2, NAXIS3) = (xsize, ysize, modes).

    moka measlinresp [-a AMPL] measures the response to the cube in calib/RMmodesDM.fits (made by mkpokes or dropped there by hand). It needs CompUs acquWFS, mlat and measlinresp, the latency of a past moka mlat (work/fps.<mlat FPS>.datadir/cacaovars.bash, kept by teardown), and the streamin stream, whose shape must match the cube's. Everything else comes from the measlinresp FPS conf; -a sets ampl until the next deploy. All files are in <rootdir>/calib/:

    File Is
    RMmodesWFS.inprogress.fits what the run writes, rewritten at every cycle
    RMmodesWFS.fits a complete run only (procinfo.loopcntMax cycles), renamed at its end
    RMmodesWFS.prev.fits the RMmodesWFS.fits that was there when the latest run began

    Every moka measlinresp measures again. Nothing checks that other writers leave the DM alone: run it before moka runstart.

    moka mkcm [FLAVOR] [-n NMODES] [-r REG] computes the control matrix pair from whatever response matrix pair is in <rootdir>/calib/ (RMmodesDM.fits, RMmodesWFS.fits: measured or dropped there by hand) and writes CMmodesWFS.fits and CMmodesDM.fits there, float32. It touches no stream, so it also runs on a pipeline that is not deployed. The loop computes the mode coefficients a = CMmodesWFS · wfs and the DM command dm = CMmodesDMᵀ · a, so both cubes have the same number of slices. With the response W (one row per poke mode) decomposed as V · diag(σ) · Uᵀ, σ descending:

    • tsvd (default): one slice per kept singular mode, u_k / σ_k and the DM shape v_kᵀ · D.
    • tikhonov: the same slices with gain σ_k / (σ_k² + λ²), λ = REG · σ_0. It needs -r.
    • pinv: the pseudo-inverse restricted to the kept modes; the slices are the poke modes themselves (CMmodesDM is RMmodesDM).

    -n keeps the singular modes of index below NMODES (1 to the number of poke modes); -r keeps, for tsvd and pinv, those with σ_k > REG · σ_0 (default 1e-6: only null modes go). They combine. If no mode is kept, mkcm fails and writes nothing. Both headers hold CMFLAVOR, CMNCUT (the -n given; absent without -n), CMREG (the effective -r) and CMNKEPT (the number of singular modes kept); CMmodesWFS.fits also has an HDU SINGVALS with all singular values, to choose -n and -r from. A pair of the same parameters, newer than both RM files, is left alone; a hand-made pair (no CMFLAVOR) is replaced.

    moka spool loads the control matrix pair in <rootdir>/calib/ (CMmodesWFS.fits, CMmodesDM.fits: made by mkcm or dropped there by hand) and starts the loop with the integrator off. It needs CompUs acquWFS, wfs2modes, mfilt and modes2dm, and takes no parameter. Step by step:

    1. SetLoopOff[mfilt]: loopON false, before anything runs.
    2. RunStop[modes2dm,mfilt,wfs2modes]: they copy the matrix and the mode count at run start.
    3. LoadCM[wfs2modes,modes2dm]: each cube into the immodes stream of its CompU, as (xsize, ysize, modes). It refuses if the files are missing, their mode counts differ, or CMmodesDM.fits is not the [dmhint] size.
    4. RunStart[acquWFS]: skipped if it runs.
    5. RunStart[wfs2modes,mfilt,modes2dm]: one at a time, in that order. It waits for each run flag only; nothing checks that the stream a CompU reads exists or has the size the pair implies.
    6. SetLoopOff[mfilt]: checked again once mfilt runs.

    spool never writes to the DM. To close the loop, set loopON, loopgain, loopmult, looplimit on the mfilt FPS in milk-fpsCTRL; loopZERO zeroes the command. Run spool again after a new mkcm.

    moka takeref [-n NFRAMES | -t SECONDS] averages the next frames of aol<loop_number>_imWFS1 into aol<loop_number>_wfsref, aol<loop_number>_wfsrefc and calib/wfsref.fits, as cacao-aorun-026-takeref does; acquWFS subtracts wfsrefc into imWFS2 from its next frame.

    moka takedark [-n NFRAMES | -t SECONDS] averages aol<loop_number>_wfsim the same way into aol<loop_number>_wfsdark and calib/wfsdark.fits, as cacao-aorun-005-takedark does. It creates wfsdark when the stream is missing. The dark needs only the linkage that gives aol<loop_number>_wfsim its data source. The plan does not remove the light: a pipeline wraps it with its own tasks for that, as milk-examples/pipelines/aoloop-conf/scripts/moka_plans.py does (§4).

    run_plan(pipeline, name, compus) applies a CompU subset to every step of any plan; a plan with a pipeline-wide task (deploy, teardown) then raises ConfigError.

    2. Built-in tasks¶

    Task Goal (success())
    ClaimRundir The rundir is claimed by this rootdir for the current boot. It refuses if another rootdir holds the name, or another pipeline holds the loop_number
    InitFPS Every FPS exists and is valid. It runs fpsinit in work/, then sets the [compute_units.<cu>.fps] values
    LoadData Every [[dataloads]] target stream exists with the source FITS shape and dtype
    ConfStart Every conf process is running
    RunStart Every run process of the subset (default: runstart) is running. It starts them one at a time, in order (all at once if neither step nor conf.toml names them), and requires the conf processes to run
    RunStop No run process is running
    WaitRunEnd No run process is running. It waits up to 120 s for the runs to end by themselves and never stops anything
    SetLinResp The measlinresp FPS holds the cube and output paths (relative to work/), mlat's frame rate and latency, and -a; no RMmodesWFS.fits nor in-progress file is left (the first is archived to .prev)
    WaitLinResp As WaitRunEnd, with a timeout of 2x expected +10 s; then a complete run's in-progress file is renamed RMmodesWFS.fits
    TakeRef Never before it runs; then aol<N>_wfsref, aol<N>_wfsrefc and calib/wfsref.fits hold the float32 average of -n new aol<N>_imWFS1 frames, or of those that arrive within -t seconds
    TakeDark As TakeRef, from aol<N>_wfsim into aol<N>_wfsdark (created when missing) and calib/wfsdark.fits
    DeapplyAllLinkages No systemlinkage symlink remains
    ConfStop No conf process is running
    KillTmux No tmux session with a CompU's FPS name is left. It does nothing unless teardown_kill_tmux = true
    DestroyFPS No FPS of the subset exists
    ReleaseRundir The rundir is gone

    3. Running a single task¶

    Pipeline.task_do(task) runs one task, on its default CompUs or on a subset, without the state gate. It skips the work when success() already holds.

    from moka.operate.pipeline import Pipeline
from moka.operate.tasks import RunStart, RunStop, WaitRunEnd

pp = Pipeline("basic")
pp.task_do(RunStart)                        # (1)!
pp.task_do(RunStart(pp, ["mlat"]))          # (2)!
pp.task_do(WaitRunEnd(pp, ["mlat"]))        # (3)!
pp.task_do(RunStop(pp, ["wfscam", "dmdelay"]))
    1. The CompUs of runstart (default: all); RunStop, WaitRunEnd: every CompU.
    2. One CompU.
    3. Waits (up to 120 s) for a run that ends by itself.

    4. Custom plans¶

    A pipeline carries its own plans and tasks in its confdir, from two optional sources: [plans.<name>] tables in conf.toml, and the file scripts/moka_plans.py. Both are conf files, copied to rootdir/conf/ at init and tracked by drift. They are read from the rootdir.

    Pipeline.plans and Pipeline.tasks look a name up in the pipeline's own definitions first, then in PLANS and TASKS; run_plan, run and moka resolve names through them. A local definition with the name of a built-in one (or a Python plan with the name of a TOML plan) overrides it, with a warning. A plan named like a fixed moka command (state, plans, tasks, link, unlink, nuke) makes every moka command on that pipeline fail; run_plan is unaffected. Local definitions never change PLANS and TASKS.

    [plans.latency]
steps = [
    "RunStart[dmdelay]",
    "RunStart[wfscam]",
    "RunStart[mlat]",
    "WaitRunEnd[mlat]",
    "RunStop[wfscam,dmdelay]",
]
# on_failure = "abort"
# accepts = "consistent"
# help = "One line, for moka -h."

    A step is Task or Task[cu1,cu2]. Only the syntax is checked at load; task and CompU names are checked when the plan runs. compus_arg is not settable in TOML, so a [plans.runstart] or [plans.runstop] table that overrides the built-in loses its [CU]... arguments; use moka_plans.py to keep them.

    from moka.operate.plans import Plan, Step
from moka.operate.tasks import Task

class AcquireDark(Task):
    ...

TASKS = [AcquireDark]   # (1)!
PLANS = [Plan("dark", (Step("AcquireDark"),))]
    1. Registered under the class name.

    A plan can wrap a built-in one that it overrides:

    from dataclasses import replace
from moka.operate.plans import PLANS as BUILTIN, Step

_takedark = BUILTIN["takedark"]
PLANS = [replace(_takedark, steps=(Step("RemoveLight"), *_takedark.steps, Step("PutbackLight")))]

    Both lists are optional. The file is imported, not sandboxed: it is trusted like a command hook.

    From Python, run(pipeline, plan) runs any plan, registered or not, and PLANS.register(name, plan) adds a plan for every pipeline of the current process:

    from moka.operate.plans import Plan, Step, run

run(pp, Plan(
    "restart_wfs",
    (
        Step("RunStop", ("wfs",)),       # only CompU "wfs"
        Step("RunStart", ("wfs",)),
        Step("WaitRunEnd"),              # all CompUs
    ),
    on_failure="abort",
    accepts="consistent",
))
    Field Type Default Meaning
    Step.task str — A task name of the pipeline, which is the task's class name
    Step.compus tuple[str, ...] \| None None The CompU subset; None: the task's default, all CompUs for most (see the top of this page). Unknown names raise ConfigError
    Plan.name str — The plan's name, which is also the moka command name. In TOML, the table name
    Plan.steps tuple[Step, ...] — The steps, run in order
    Plan.on_failure "abort" \| "best_effort" "abort" abort stops at the first failing step and raises its error. best_effort runs every step, then raises one BestEffortError that lists the failures
    Plan.accepts "consistent" \| "cold_or_consistent" \| "any" "consistent" The states the plan may start from. consistent refuses cold and inconsistent, cold_or_consistent refuses inconsistent, and any refuses nothing
    Plan.compus_arg bool False True: its moka command takes [CU]... and runs every step on those CompUs. Not settable in TOML
    Plan.params tuple[Param, ...] () Values its moka command takes, handed to every task of the plan (below). Not settable in TOML
    Plan.help str "" One line for moka -h and moka <plan> -h. In TOML: the help key

    A step with a CompU subset appears in messages as Task[cu1,cu2].

    A Param(name, type=str, default=None, positional=False, short=None, help="", choices=None) adds [NAME] (positional) or -<short>/--<name> NAME to the plan's command; type is str, int or float. Every task of the plan receives the same dict as self.params, without the values left at None; a task reads only the keys it knows, and must work with an empty dict (moka plans and moka tasks build it so). From Python: run_plan(pp, "probe", params={"ampl": 0.5}), or run(pp, plan, params).

    Plan("probe", (Step("Probe"),), params=(Param("kind", positional=True), Param("ampl", float, short="a")))
# moka probe -p basic hadamard -a 0.5   →   self.params == {"kind": "hadamard", "ampl": 0.5}

    help is the option's help in moka <plan> -h. choices, a tuple of strings, restricts the value: anything else is a usage error (exit code 2).

    A task of your own subclasses Task; see Internals: task contract.

    5. How a plan runs¶

    run_plan(pipeline, name), run(pipeline, plan) and moka <name> run a plan in three phases.

    flowchart LR
    B["<b>Build</b><br/>instantiate every step's task"]
    G["<b>Gate</b><br/>compute the state,<br/>check it against accepts"]
    D["<b>Do</b><br/>task_do each step in order,<br/>apply on_failure"]
    E1["ConfigError<br/>nothing changed"]
    E2["refused<br/>nothing changed"]
    B --> G --> D
    B -- "unknown task or CompU" --> E1
    G -- "state not accepted" --> E2
    1. Build. An unknown task or CompU name raises ConfigError here, before anything has changed.
    2. Gate. The state is computed once and checked against accepts.
    3. Do. pipeline.task_do(task) runs for each step, in order. abort stops at the first failure; best_effort runs every step, then raises one BestEffortError.

    Progress goes to the moka.plan logger at INFO, with the data in the record's moka attribute.
